# Архитектура Telegram Reader

Один владелец, один процесс TDLib и один поток приёма. Прикладные операции
чтения используют официальный MCP SDK и доступны по stdio и Streamable HTTP.
Вход в Telegram и настройки доступа выполняются через локальную CLI.


```text
Codex -> stdio MCP SDK -> LivePolicyTools -> ReadTools -> TDLib
MCP-клиент -> HTTPS + OAuth -> то же ядро
```

Конфигурация и сессия TDLib хранятся вне каталога выпуска. В режиме stdio
Codex запускает локальный процесс. HTTP использует OAuth с PKCE, проверками
Host/Origin и может быть доступен через TLS-прокси.

## Скорость и объём

- Клиент MCP 2026-07-28 может сразу вызвать инструмент или сначала запросить
  `server/discover`. Клиенты предыдущих версий используют `initialize`.
  Для чтения по известным ID достаточно одного вызова нужного инструмента.
  `telegram_status` служит для проверки состояния подключения.
- `getChat` уже читает локальные данные TDLib. Дополнительный Python chat-cache
  не введён: он дублирует память и может устареть при изменении защиты чата.
  Решения ACL и сообщения не кешируются.
- Контроль размера страницы считает точный прирост сериализованных элементов.
  Вместо повторного кодирования всего растущего списка каждый элемент кодируется
  отдельно; формат ответа и консервативный лимит 48 КиБ внутреннего tool result сохранены
  (внешний JSON-RPC envelope учитывается отдельно).
- `max_text_chars=0..4000` в истории/поиске уменьшает текст каждого сообщения;
  default 4000 совместим с 0.1. Для обзора подходят короткие выдержки, затем
  `get_message` для выбранных ID. Усечение всегда отмечается `text_truncated`.
- MCP `content` и `structuredContent` сохраняются для совместимости, поэтому
  текст физически присутствует дважды. Байты ответа и каталога измеряются отдельно;
  число токенов зависит от host/model и не подменяется числом символов.
- Прогретый процесс переиспользует одно соединение TDLib. Измерения CPU/serialization
  на искусственных данных не измеряют Telegram network RTT, tunnel latency или
  время ответа модели. SDK добавляет зависимости и стоимость холодного импорта;
  меньший общий RAM/размер относительно stdlib 0.1 не заявляется.

## Ограничения нагрузки и актуальности

У действующего туннеля сохранён лимит 2 concurrent requests/max-inflight.
В самом сервере до 16 одновременно работающих MCP tool workers; избыточные вызовы отклоняются,
не ждут в очереди потоков. До 8 реально отправленных запросов TDLib, включая те,
чьи Python callers уже получили timeout: слот освобождает поздний ответ или close.
Это предотвращает бесконтрольные native retries. После 429 новый запрос немедленно
получает безопасный `telegram_rate_limited` и доступный `retry_after_seconds`;
автоматических повторов и sleep в обработчике нет. Если все native-запросы зависли,
новые чтения отклоняются до ответов или перезапуска, а не обходят предел.

Общий budget tool — 25 секунд, TDLib request — максимум настроенного timeout
(default 20). Абсолютный deadline проверяется перед отправкой после ожидания lock.
Idle `td_receive` ждёт до 1 секунды вместо 0.1, но входящий ответ будит его сразу.
Единственный metadata cache — до 100 папок: title 256, icon 64, whitelist скаляров.
Он очищается при потере авторизации/ошибке/закрытии и никогда не хранит сообщения.
Полученный payload и завершённый Future не удерживаются receive loop между вызовами.

HTTP/stdio ограничивают входной record 64 КиБ. Штатный SDK может создавать задачи
ответов для недоверенного stdio peer, который перестал читать stdout; лимит workers
не является пределом всех SDK tasks. Stdio рассчитан на доверенный tunnel/local host.
При открытом idle stdin отмена ждёт blocking readline; штатное завершение — закрытие
pipe со стороны туннеля, затем ограничения systemd. Собственный transport для обхода
этих ограничений не вводился.

## Политика и страницы

Каждый вызов инструмента перечитывает приватную конфигурацию. Каталог инструментов
строится из статических схем. `selected`, `channels` и
`all` имеют прежнее значение; истечение проверяется перед обращением и после ответа.
Текущий snapshot уже начатого вызова действует в пределах его budget. Конфигурация
не переписывается миграцией. Разрешение all не запускает выгрузку и не добавляет
методы отправки/изменения. Названия папок остаются отдельной разрешённой metadata.

`list_chats` all/folder — ограниченный загруженный префикс, не полный обход аккаунта.
Поиск чатов тоже может быть неполным. `read_history` и `search_messages` возвращают
не более 50 сообщений и exclusive cursor; inclusive TDLib anchor отбрасывается.
Отфильтрованные строки могут дать пустую страницу с cursor. Чужой chat_id не двигает
cursor, дубликаты убираются, нарушение убывающего порядка вызывает ошибку.
При byte limit cursor не перескакивает непоказанное сообщение.

`telegram_get_photo` проверяет доступ к чату и сообщению по `chat_id` и
`message_id`. Возвращает превью до 192 КиБ или крупнейший доступный JPEG
до 1 МиБ без перекодирования.

Файлы/чатовая/сообщенческая базы TDLib отключены; необходимая авторизационная сессия
сохраняется. Облачный `searchChatMessages` работает без message database:
это проверено в [закреплённом MessagesManager.cpp](https://github.com/tdlib/td/blob/9d92b49bc5d0d2e29fe518239af647a88f8680e6/td/telegram/MessagesManager.cpp#L16938).
Secret Chats не поддерживаются. Полнота истории и поддержка вложений не обещаются.
